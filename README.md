# 知乎问人

> **让 AI 知道，什么时候应该把问题还给人。**

一个建立在知乎内容、创作者与现有咨询能力之间的**问题智能路由层**。

它不替你回答人生问题，它帮你找到**真正经历过类似选择的人**。

两个入口，同一份语料、同一个内核（**证据必须可回溯到原文**）：
**先说你的问题**（问题找人），或者**从专业领域逛起**（领域社交）。

## 它解决什么问题

### 一、AI 让「得到答案」越来越便宜

过去，你有问题会去搜索、读几个回答、自己形成判断。现在大模型可以几秒钟把公开信息检索、总结、讲清楚。

**大量标准化知识问题，正在从「内容消费」变成「AI 直接回答」。**

这对知乎提出了一个真问题：当 AI 越来越擅长总结公开知识，十几年积累的真人社区，还有什么不可替代的价值？

### 二、真正难的问题，缺的不是答案，是可参考的经历

但有一类问题没有标准答案 —— 职场、升学、创业、专业实践：

> 「我该不该去这家创业公司？」
> 「传统行业转 AI，我这个年纪还有机会吗？」
> 「第一次被要求带团队，我该接吗？」

这些问题的答案强依赖**你的处境**：你的阶段、你的风险承受度、你的家庭、你手上的约束。搜到的往往是「创业公司优缺点」「转行需要学什么」—— 这些是**观点**，不是你需要的**经历**。

你真正想知道的是一句话：**「有没有真正做过类似选择的人，他当时是怎么判断的？」**

### 三、现有路径并不差，但有一个关键缺口

你现在的路径是：搜索帖子 → 找到答主 → 点进主页 → 私信或付费咨询。这条路径是通的，我们**不打算改造它**。

真正的缺口发生在**你已经决定想找真人、却不知道该找谁**的那一刻：你只能把复杂处境硬翻译成几个搜索关键词，然后在一堆「相关但不贴身」的内容里翻找，或者干脆去找那个粉丝最多的大 V —— 哪怕他的经历跟你的处境根本不沾边。

**知乎问人补的就是这一步。** 它补的是「我知道我的问题，但不知道谁真的懂」。

## 一次使用是什么样的

你用**自己的话**描述问题，带上你的处境和纠结点，比如：

> 我在大厂做产品 7 年，收到一家 50 人 AI 创业公司产品负责人的 offer，固定薪资降 20% 但有期权和管理机会，同时我在这里晋升已经放缓，该不该去？

系统做四件事：

```
① 分诊   这个问题该由公开内容、AI，还是真人回答？
         ↓ 只有高度情境化的问题才继续往下走
② 理解   把它拆成结构：当前状态 / 目标 / 变化 / 约束 / 需要什么经历
         ↓
③ 找经历 在全站内容里检索「经历事件」——
         不是找「相关文章」，是找「谁真的做过这个选择」
         关键词 + 语义混合召回，再按决策相似度重排
         ↓
④ 校验   每一条推荐理由，都必须能回到原文的一句话
         找不到证据就不说，宁可不推
```

最后你拿到的不是一段答案，而是**三个人**，每人一张卡片：

| 字段 | 示例 |
|---|---|
| **推荐角色** | 推荐 1｜经历最接近 |
| **人物** | 林一舟 · 互联网行业产品经理 |
| **为什么推荐** | 曾经历「大厂 Senior PM → AI 创业公司产品负责人」，与你当前处境高度相似 |
| **内容证据** | 从《从大厂 Senior PM 到 50 人 AI 创业公司产品负责人，我踩过的三个坑》里逐字引出的原句 |
| **与你最相关** | 同样涉及「大厂」「创业公司」「降薪」「期权」 |
| **不适合回答** | TA 的内容里没有覆盖你关心的「期权定价」；目前只找到 1 条相关公开内容 |
| **下一步** | 看相关内容 / 看 TA 主页 |

**「不适合回答」是必显项，不是彩蛋。** 一张诚实的卡片，比一张看起来很厉害的卡片有用。

### 那「别问人」是什么意思

如果检索发现你的问题**公开内容已经足够回答**，系统会直接给你内容，并明确告诉你：**这个问题不用打扰真人。**

这是刻意的设计。一个只想着把人往付费咨询推的产品，短期数据会更好看，长期会失去信任。我们宁可少一次转化，也要守住「只在真的需要时，才把人推给真人」这条线。

## 和现有方式有什么不同

| | 擅长 | 主要缺口 |
|---|---|---|
| **知乎搜索** | 关键词明确、答案已存在 | 容易找到「相关内容」或大 V，但难以判断谁真的经历过 |
| **通用 AI** | 总结、解释、比较 | 替代不了具体经历和隐性判断 |
| **现有付费咨询** | 与**已知**答主完成交易 | 需要你先知道该找谁 |
| **知乎问人** | 问题 → 经历 → 真人 | 补齐「我知道问题，但不知道谁能回答」这一步 |

对比 LinkedIn / 传统专家平台：

| 维度 | LinkedIn / 传统专家平台 | 知乎问人 |
|---|---|---|
| 核心图谱 | 职业身份、技能、服务 | **内容证据、经历事件** |
| 入口 | 找某类人 / 找某项服务 | **先说「我遇到了什么问题」** |
| 排序目标 | 谁更专业 / 更有资历 | **谁的哪段经历对这个问题最有用** |
| 信任来源 | 公司、职位、资质、评价 | **与当前问题直接相关的内容原文** |
| AI 角色 | 提升搜索 / 服务发现效率 | **问题分诊 + 经历检索 + 证据组织** |

一句话概括差异：

> **LinkedIn 回答「这个人做过什么工作」；知乎问人回答「这个人真正经历过、思考过什么问题」。**

而这门生意的底气来自数据本身 —— 因为知乎的搜索接口能拿到真实长文，而它**不返回作者主页标识**，所以我们的数据流天然是：

> **先用问题搜内容 → 从内容抽经历 → 再按作者聚合成「人」。**

我们不认识你，我们只认识你写过什么。

## 三个设计立场

**1. AI 不替人社交，只负责分诊、检索和证据组织。**
AI 做：判断该不该问人、理解你的处境、检索经历、组织证据。
AI 不做：不做最终人生选择、不自动发私信、不编造经历。

**2. 「写过」≠「经历过」。**
这是整个产品的护城河。一段内容被判定为「经历」，必须满足：第一人称叙述、有具体的决策与约束、有可回溯的时间线索，而且**推荐理由里的每一句话都能定位回原文**。找不到证据就不说。

**3. 先免费给价值，再让你决定要不要交易。**
先给你「为什么推荐」和内容证据，允许你先读原文、先看主页。公开内容够用的时候，主动劝退。信任是长期资产。

## 现在做到什么程度

**本地可运行的原型，核心链路端到端跑通，并且已有对照数据说明它比关键词搜索强。**

一次提问会真正走完 8 个步骤，页面上能直接看到每一步产出了什么：

```
01 分诊        路由 → human
02 结构化      4 条检索词 · 阶段 有 7 年经验
03 混合召回     29 条内容（keyword+semantic）
04 经历抽取     4 条
05 聚合创作者   4 位候选
06 重排        4 条
07 证据校验     4 位候选（证据可回溯）
08 生成卡片     3 张推荐卡片            总耗时 ~110ms
```

同一次运行的指标：**召回 29 · 经历 4 · 候选 4 · 证据覆盖率 100%**。

### 它比关键词搜索强多少

我们在 168 条语料 / 20 个真实职场问题上跑了三组对照（同一套代码，只是配置不同）：

| 组 | 配置 | Top-3 有效人选率 | 至少命中 1 位亲历者 | 证据覆盖率 |
|---|---|---|---|---|
| A | 纯关键词检索 | 40.7% | 72.2% | 0% |
| B | 纯语义检索 | 35.2% | 66.7% | 0% |
| **C** | **完整链路** | **54.6%** | **72.2%** | **100%** |

最有说服力的一处：在「IC 转管理」「AI 转型」那类问题上，
**A 组经常 0/3 —— 关键词命中的是方法论文章**；
C 组靠「经历抽取 + 逐字证据校验」能识别并捞出真亲历者。

```bash
npm run gold:build && npm run eval   # 复现这张表，产出 eval/report.md
```

> 完整的方法学、指标定义与局限声明见 [DEMO.md](DEMO.md) §5。
> 我们主动声明了四个局限（含「语料是合成的」「B 组是弱基线」）——
> 评审最可能质疑的不是代码，是「证明不了」。

### 另一条入口：从专业领域找人

除了「先说问题」，还有一条路径是**按领域浏览**。它用同一份真实语料，先把内容归拢成
**领域 → 细分议题 → 正在这个议题上实践的人**：

```
领域    Agent 开发 · 人工智能应用 · 金融科技 · 数据建模 · 产品与创业 · 独立开发 · 科研与工程实践
议题    每个领域下 2~3 个，如「Agent 架构与源码」「工具调用与协议」「评测与可靠性」
人物    从真实内容算出来 —— 谁在哪些议题上写过、写了多少
```

**领域名称是我们人工定义的，但人不是。** 这一点很关键：领域名属于产品叙事，
必须可控、可讲、可评审（所以不用聚类，聚类结果无法解释）；而「谁属于哪个议题」
全部由真实知乎内容算出来，**绝不编造人物** —— 这跟 8 步链路的「证据驱动」是同一个内核。

实测挂载：Agent 开发 28 人 ｜ 人工智能应用 47 人 ｜ 金融科技 14 人 ｜ 数据建模 9 人 ｜
产品与创业 49 人 ｜ 独立开发 13 人 ｜ 科研与工程实践 11 人。

星图的**坐标由后端算好**（0~1000 画布，中心是当前领域），而且是确定性的 ——
**刷新页面位置不会变**，演示时这点很重要。前端只需等比缩放到容器，不用自己实现布局。

两条路径共用同一份语料，但**边界是清楚的**：领域搜索只返回领域、不返回人物；
找人就只返回人。破了这条边界，两个功能就糊在一起了。

| 能跑 | 待补 |
|---|---|
| 分诊（公开内容 / AI / 真人三路由） | **真 Embedding 后端**（默认 hash 降级，见 DEMO §5 局限 3） |

## 技术实现

**核心链路是确定性的工作流，不是 Agent Runtime。**

这不是能力取舍，是主动选择：因为我们要跑**可复现的对照实验**（三组配置必须走同样的步骤），也要保证**证据链可审计**（每段经历必须能回溯到原内容）。模型的自主规划会让这两件事同时失效。需要自主性的只有一处 —— 召回不足时自动改写检索词重试，用有界循环在流程内解决。

| | |
|---|---|
| 前端 | Next.js 15（App Router）+ React 19 + TypeScript + Tailwind CSS |
| 后端 | Next.js Route Handlers（Node runtime），单进程 |
| 大模型 | 知乎直答（OpenAI 兼容接口），可切换任意兼容服务 |
| 数据 | 知乎开放平台 API；另有本地 fixture 模式，**零凭证可跑通全链路** |
| 生产依赖 | **只有 3 个包**，`npm audit` 为 0 漏洞 |

**隐私与安全**

- 知乎账号全程走标准 OAuth 授权，我们不接触、不保存你的密码。
- 授权凭证用 AES-256-GCM 加密后存放在 **HttpOnly Cookie** —— 浏览器脚本读不到，服务端不落库。
- 服务端只读取**公开范围**的内容；不批量爬取、不滥用站内数据。
- 对外展示的所有推荐理由都必须绑定原文出处，不输出无法溯源的判断。
- `/api/health` 只回状态布尔值，不回任何密钥内容。

架构细节、扩展方式与全部工程边界见 **[DEVELOPER.md](DEVELOPER.md)**。

## 自己跑起来

需要 Node.js 18.18+（推荐 20/22）。

```bash
git clone <repo-url> && cd zhihu-ask
npm install

# 零凭证模式：不接任何外部接口，用本地样例内容跑通全链路
cp .env.example .env.local
sed -i 's/^USE_FIXTURES=0/USE_FIXTURES=1/' .env.local
sed -i "s|^SESSION_SECRET=.*|SESSION_SECRET=$(openssl rand -hex 32)|" .env.local

npm run dev        # → http://localhost:3000
```

打开后点「示例 1」→「开始问人」，就能看到完整链路。

### 接入真实数据

在 [知乎开放平台个人中心](https://developer.zhihu.com/profile) 生成 **Access Secret**，填进 `.env.local` 的 `ZHIHU_ACCESS_SECRET`，再把 `USE_FIXTURES` 改回 `0`。

想用「知乎账号登录」读取你自己的关注与收藏，还需要申请 OAuth 应用（`ZHIHU_APP_ID` / `ZHIHU_APP_KEY`）。**注意：知乎不接受 `localhost` 作为回调地址**，所以真实登录必须先部署到有公网 HTTPS 域名的环境。

部署前推荐先打一次自检接口，它会告诉你缺什么凭证、数据目录是否可写：

```bash
curl -s https://你的域名/api/health | python3 -m json.tool
```

## 数据来源与合规

- 内容与用户数据来自**知乎黑客松官方开放的 API**（[开放平台](https://developer.zhihu.com/)），按官方配额使用，并在应用层做了缓存与限额保护。
- 本项目**只读取公开范围**内容，不做批量爬取，不滥用站内用户数据。
- 三个凭证（App ID / OAuth App Key / 开放平台 Access Secret）分开存储、分开使用，不写入代码仓库。
- 引用他人内容时保留作者名与原文链接。
- 知乎已知的协议限制（例如授权回调不返回 `state`、没有 token 撤销接口）我们如实处理并在界面与文档中标注，**不声称具备生产级安全能力**。

## 项目结构

```
src/
├── app/        Next.js 路由壳 —— 只转发，不放业务
│   ├── page.tsx          项目推荐页（零后端）
│   ├── app/              授权门 + 功能首页 · /app/find 问题找人
│   └── api/              auth/* · agent/search · fields/* · health
│
├── back/       ★ 后端
│   ├── steps/            8 步业务链路（核心）
│   ├── domain/           领域定义、图表构建、阶段映射、实验配置
│   ├── framework/        工作流引擎、缓存、额度护栏、限流  ← 不知道业务是什么
│   ├── adapters/         知乎 HTTP / OAuth / LLM / 本地样例数据源  ← 唯一装配根
│   ├── handlers/         业务处理（脱离 Web 框架也能测）
│   └── fixtures/         语料：合成 174 条 + 真实 180 条
│
├── front/      ★ 前端
│   ├── pages/            页面实现
│   ├── components/       展示组件
│   └── api-client.ts     前端唯一的请求出口
│
└── shared/     ★ 前后端唯一交接点
    └── contract.ts       端点常量 + 统一信封 + 所有「过线」的类型
```

依赖方向是单向的：`back → shared ← front`。`front/` 不允许 `import @/back/*`，

### API

| 端点 | 说明 |
|---|---|
| `POST /api/agent/search` | 问题找人。返回 8 步 trace + **六阶段进度** |
| `GET /api/fields/featured` | 推荐领域（7 个） |
| `GET /api/fields?query=&limit=` | 领域搜索 —— **只返回领域，不返回人物** |
| `GET /api/fields/:id/graph` | 领域星图。议题与人物**都带后端算好的坐标** |
| `GET /api/auth/session` | 登录状态：`configured` / `authenticated` / `user` |
| `GET /api/auth/zhihu/login` · `/callback` · `/logout` | 知乎 OAuth 全流程 |
| `GET /api/health` | 能力自检（含当前在跑哪份语料） |
